## 3. Phase 5 AI implementation

All four generation flows now follow **generate → review → edit → save**, with nothing written to the database until a human clicks Save:

- **Strategy generation:** `POST /api/ai/strategy` generates and validates a draft (summary, monthly theme, pillars, strategic recommendations) and returns it — no `content_strategies`/`content_pillars` row is created. `strategy-view.tsx` shows an editable review card (edit summary/theme/pillar name/description/percentage, remove a pillar) with Regenerate/Discard/Save Strategy actions. `saveGeneratedStrategyAction` persists it, recording `source: "AI"` or `"AI_EDITED"` depending on whether anything was changed before saving.
- **Pillar generation:** pillars are generated as part of the strategy draft above (the spec allows either a combined or separate flow; this repo's existing architecture always generated pillars alongside the strategy, so that pairing was preserved rather than artificially split).
- **Ideas generation:** `POST /api/ai/ideas` now also accepts optional `platform`/`objective`/`format` generation inputs (per the spec's "user options" list) and returns a draft list — each idea includes title, description, pillar, and now also `recommended_platform`/`recommended_format`/`content_objective`/`suggested_hook` (extended in `lib/ai/schemas.ts`'s `aiIdeaSchema` and the prompt in `generate-ideas.ts`). `ideas-view.tsx` shows each as a selectable, editable card; `saveGeneratedIdeasAction` persists only the ones the user leaves checked. The suggestion fields are shown for review but not persisted, since the existing `content_ideas` schema doesn't carry them and extending it wasn't necessary to satisfy the review requirement.
- **Calendar generation:** `POST /api/ai/calendar` returns the full generated post set as a draft (with a temporary client-side key per post) instead of bulk-inserting. `calendar-detail-view.tsx` shows every draft post (date, editable title/platform/pillar/format, brief), with per-post removal, Regenerate (full batch), Discard, and Save Calendar. `saveGeneratedCalendarAction` re-checks the calendar is still empty before writing (guards a two-tab race) and bulk-creates the accepted posts.
- **Post generation/regeneration:** `POST /api/ai/post` (topic/alternative-angle/caption/improve/field regeneration) no longer calls `updatePost` — it returns generated field values only. `post-detail-dialog.tsx` merges them into its existing local (unsaved) editing state and marks the form dirty; the dialog's pre-existing manual "Save" button is what actually persists it, so an AI regeneration the user dislikes is discarded for free by simply not saving. A small "Unsaved changes" indicator appears next to Save when there's anything pending.
- **Platform-aware AI:** already present pre-Phase-5 in the generators (per-platform prompt content); the ideas generator was extended to recommend a platform per idea; not otherwise rebuilt, since the existing implementation already varied its prompts by the calendar's/idea's target platform.
- **Cost control / no background generation:** confirmed every generation call site is a direct result of a button click (Generate Strategy/Ideas/Calendar, or a specific regenerate/improve action) — the one automatic trigger, `calendar-detail-view.tsx`'s `autoGenerate` prop, fires only immediately after the user's own "create calendar and generate" action on the previous screen, not on a timer or on mount independent of user intent.
- **AI generation history:** unchanged structurally (already solid per the inspection); generation records now additionally note `saved: false` in `output_summary` for every generate call, reflecting that generation and persistence are now two separate steps.

## 4. Phase 6 intelligence

New `lib/intelligence/` module — pure, unit-tested functions, no new tables, no AI calls:

- **Calendar analysis / content gaps** (`gap-detection.ts`): no upcoming content at all; a 7+ day gap between two consecutive upcoming posts; heavy concentration (80%+) on one content format.
- **Content mix** (`content-mix.ts`): compares the strategy's planned `content_mix` percentages against the calendar's actual per-pillar post distribution, flagging a ≥20-point gap in either direction with a plain-language message.
- **Pillar balance** (`pillar-balance.ts`): classifies each pillar unused / underused / balanced / overused against its `recommended_percentage`.
- **Completion tracking** (`completion.ts`): planned/completed/draft/overdue counts, where overdue = scheduled in the past and not completed.
- **Quality signals** (`quality-signals.ts`): factual, per-post completeness checks only (no CTA / hook / caption / hashtags / creative direction / pillar) — no invented scoring system, exactly per the spec's caution against presenting subjective judgment as fact.
- **Dashboard insights** (`dashboard-insights.ts`): aggregates all of the above plus a next-post callout and a draft-count nudge into a capped (5), priority-ordered list.

Wired in: a new "Insights" card on the Dashboard (built from posts across every calendar in the workspace, not just the active one; hidden entirely when there's nothing to say, and only reachable once a workspace is past its own first-run empty state, so brand-new workspaces are never nagged); a `QualitySignals` component dropped into the post detail dialog; and **Duplicate Idea**, rounding out the spec's "duplicate ideas/posts/calendars" requirement — Duplicate Post and Duplicate Calendar already existed in the repository pre-Phase-6 and needed no changes.

**Not implemented in Phase 6:** no automatic content movement (gaps and imbalances are reported, never acted on — the user remains in control, per the spec's explicit instruction); no social media publishing of any kind (out of scope per the spec).

## 8. Known limitations

Documented explicitly per the spec's "do not hide known problems" instruction, and per its caution not to claim an AI feature is production-ready without a real funded API:

- **No live test against a real, funded OpenAI API key.** This sandbox has no network path to the OpenAI API (or to a real Supabase project), so every AI code path was verified by static review, type-checking, and the existing zod-validated-response architecture — not by an actual end-to-end generation call. The review-before-save UI (draft state, editing, save actions) was verified structurally (types line up, the API contracts match what each component reads/sends, build succeeds) but not exercised against a live model response. A real funded-API smoke test is strongly recommended before considering Phase 5 fully signed off.
- **Calendar generation's loading experience is still a client-side fake timer**, not real server-driven progress. `lib/ai/generate-calendar.ts` already has a per-stage `onStage` callback half-wired for this (noted in the original inspection), but actually streaming that to the client would need Server-Sent Events or similar — out of scope for this pass given the size of the rest of the work; the existing fake-timer `GenerationOverlay` still gives a reasonable "Understanding your brand… → Preparing your content plan…" experience, just not one tied to real progress.
- **Ideas review doesn't persist the AI's suggested platform/format/objective/hook**, only title/description/pillar (see section 3) — a deliberate scope decision to avoid an unnecessary schema change, but it means that context is visible during review and then discarded if not acted on immediately (e.g. by using it when later adding the idea to a calendar).
- **Carried forward from the Phase 4 report, still true:** no dedicated `/app/ideas/[ideaId]` or `/app/strategy/[strategyId]` detail routes (editing happens via existing modals); the post detail workspace remains a modal rather than the spec's literal `/app/calendars/[calendarId]/post/[postId]` route (query-param deep-linking was added instead, per the Phase 4 report).
